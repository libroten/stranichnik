**Что, скорее всего, происходит**

Главная причина не в ghost и не в hover-анимациях, а в последовательности в [Views/MainWindow.axaml.cs](/Users/pavel/projects/stranichnik/Views/MainWindow.axaml.cs):

1. `CompleteTreeDrag(...)` переносит элемент через `MoveItemToFolderStart(...)`.
2. Потом `ClearTreeDrag()` скрывает все placeholder-ы, снимает dim/source state, скрывает ghost.
3. Только после этого через `Dispatcher.UIThread.Post(...)` вызывается компенсация скролла.

То есть у нас получается рискованный порядок:

```text
изменили дерево
убрали placeholder-ы из layout
Avalonia пересчитала layout
пользователь может увидеть промежуточный кадр
потом отдельной задачей сдвинули ScrollViewer.Offset
```

Avalonia docs прямо подтверждают важные куски этой картины: `IsVisible=false` исключает control из layout и rendering, а layout проходит measure/arrange и перерисовку при изменениях дерева/детей. Еще `Post` именно ставит работу в очередь UI thread, а не выполняет ее атомарно в тот же layout-кадр. Источники: [Avalonia Layout](https://docs.avaloniaui.net/docs/layout/), [Threading model](https://docs.avaloniaui.net/docs/app-development/threading), [ScrollViewer](https://docs.avaloniaui.net/controls/layout/containers/scrollviewer).

**Почему на drop заметнее, чем на start drag**

На старте drag мы в основном добавляем placeholder-ы и показываем ghost. Контекст еще “рядом”.

На drop одновременно происходит больше:
- элемент удаляется из старого каталога;
- элемент вставляется в новый каталог;
- все placeholder-ы исчезают из layout;
- все dim/source/hover состояния сбрасываются;
- ghost исчезает;
- потом отдельным тиком применяется scroll compensation.

Это больше шансов на кадр “до компенсации”.

**Лучшие варианты**

1. **Синхронная компенсация до следующего render**

Самый практичный первый фикс.

Идея: после изменения модели и скрытия placeholder-ов принудительно выполнить layout pass, найти новую позицию якоря и сразу выставить `ScrollViewer.Offset`, не через `Dispatcher.UIThread.Post`.

В Avalonia есть `UpdateLayout()`, но docs предупреждают, что обычно явно вызывать его не нужно. Здесь это как раз редкий UI-случай, где мы сознательно хотим убрать промежуточный кадр.

Примерно:

```text
запомнили anchor Y
перенесли элемент
скрыли placeholder-ы
BookmarksScrollViewer.UpdateLayout()
нашли новый Y
сразу выставили Offset
только потом позволили кадру отрисоваться
```

Плюсы: минимальный рефакторинг, вероятно, сильно уменьшит промаргивание.

Минусы: принудительный layout может быть дорогим на больших деревьях. Для текущего объема данных, думаю, нормально.

2. **Не скрывать placeholder-ы через IsVisible сразу**

Сейчас `IsVisible=false` мгновенно выбрасывает placeholder из layout. Поэтому opacity transition на исчезновение не спасает: control уже не участвует в layout/render.

Можно сделать двухфазно:
- сначала `Opacity -> 0`, но место еще занято;
- после 100 ms поставить `IsVisible=false`.

Плюсы: визуально мягче.

Минусы: layout все равно изменится позже. Если не сочетать с компенсацией, “скачок” просто отложится. Я бы не начинал с этого.

3. **Держать ghost еще один кадр после drop**

При drop не скрывать ghost мгновенно, а оставить его поверх интерфейса до завершения компенсации, потом fade out.

Плюсы: пользователь смотрит на ghost, а не на перестройку списка.

Минусы: это маскировка, не устранение причины. Но как дополнение к варианту 1 может быть очень хорошо.

4. **FLIP-подход**

Классическая техника: First, Last, Invert, Play.

Мы измеряем позицию элемента до layout-change и после layout-change, а потом визуально анимируем разницу transform-ом, не заставляя layout “ехать” на глазах.

Плюсы: самый красивый результат.

Минусы: заметно сложнее. Нужно временно рисовать переносимый элемент/строку в overlay или управлять transform реального элемента. Для нашего дерева это может стать хрупко.

5. **Сильнее переписать модель отображения: flat visible list**

Сейчас дерево рекурсивное: много вложенных `ItemsControl`, много локальных `IsVisible`, много layout-участков. Можно сделать один плоский список видимых строк с `Depth`, `Parent`, `Kind`, `IsPlaceholder`.

Плюсы: DnD, placeholder-ы и компенсация станут проще и предсказуемее. Один список, один поток layout.

Минусы: это уже архитектурный рефакторинг UI. Я бы не делал сейчас, пока текущая модель не уперлась в стену.

**Моя рекомендация**

Начать с варианта 1: убрать `Dispatcher.UIThread.Post` из drop-компенсации и попробовать синхронный `UpdateLayout()` перед расчетом нового offset.

Если этого недостаточно, вторым шагом добавить вариант 3: не прятать ghost до завершения компенсации, а скрывать его после стабилизации кадра.

Я бы не трогал FLIP и flat list прямо сейчас: они сильные, но слишком тяжелые для проблемы, которую, возможно, решит аккуратная синхронизация layout + scroll offset.
